# Рабочий стек приложений и сервисов

> Status: APPROVED  
> Authority: CANONICAL  
> Last reviewed: 2026-08-16

Этот документ отвечает не на вопрос «какие сервисы существуют», а на вопрос **какой инструмент брать для конкретной задачи в нашем процессе**.

Цель — уменьшить хаос переключений. Один тип работы должен иметь один предпочтительный инструмент, а альтернативы используются только когда у них есть понятное преимущество.

## Обозначения

| Статус | Значение |
|---|---|
| **Primary** | основной инструмент для этого типа задач |
| **Secondary** | используется, когда основной неудобен или не подходит |
| **Project-specific** | подключается только в проектах, где он действительно нужен |
| **Experimental** | изучается; не является частью обязательного процесса |

## Карта рабочего процесса

| Этап | Основной инструмент | Для чего |
|---|---|---|
| Формулировка идеи и продукта | **ChatGPT** | продуктовая рамка, критика идеи, JTBD, MVP, сценарии, исследования, структурирование решений |
| Длинная работа с репозиторием | **Codex** | исследование кода, планирование, реализация, тесты, review, документация |
| Репозитории и история решений | **GitHub** | source of truth для кода, веток, PR, issues и документации |
| UX/UI и дизайн-система | **Figma** | пользовательские потоки, макеты, компоненты, прототипы, дизайн-система |
| Альтернативная работа с кодом | **Cursor** | точечная разработка и задачи, где удобнее IDE-ориентированный агентный workflow |
| UX-аудит и быстрые прототипы | **Product Design** | UX-аудит, исследование flow, варианты интерфейсов, image-to-code, URL-to-code, prototype QA |
| Автоматизация процессов | **n8n** | интеграции, фоновые workflow, webhooks, связка сервисов и AI-агентов |
| Визуальное редактирование | **Adobe / Photoshop** | ретушь, композиция, подготовка и обработка растровой графики |
| Программное видео | **Remotion** | генерация видео и анимации кодом, повторяемые видеошаблоны |
| Проверка веб-интерфейсов | **Browser / Playwright** | воспроизведение пользовательских сценариев, UI/E2E-проверки, screenshots |
| Поисковый спрос и ниши | **Yandex Wordstat** | проверка поискового спроса, формулировок и нишевых гипотез |
| Почта | **Gmail** | внешняя и рабочая коммуникация |
| Встречи и расписание | **Google Calendar** | встречи, сроки и календарный контекст |
| Контакты | **Google Contacts** | поиск и хранение контактных данных |

## 1. ChatGPT

**Статус:** Primary

Использовать для задач, где сначала нужно **понять, выбрать или сформулировать**, а не сразу менять код.

Хорошие задачи:

- продуктовый discovery;
- декомпозиция идеи;
- поиск слабых мест концепции;
- формирование MVP;
- UX-сценарии;
- сравнение решений;
- исследование внешней информации;
- подготовка документации и handoff;
- постановка задачи для Codex;
- работа с изображениями и концептами, когда это полезно для продукта.

Не использовать как единственный источник правды о состоянии репозитория, если доступен сам репозиторий.

### Типовой выход

```text
идея → решение → зафиксированный brief/flow/task → передача в Codex/Figma
```

## 2. Codex

**Статус:** Primary

Основной coding-agent для работы с реальным проектом.

Использовать для:

- изучения существующего репозитория;
- картирования архитектуры;
- составления implementation plan;
- реализации;
- тестирования;
- исправления ошибок;
- рефакторинга в ограниченном scope;
- code review;
- синхронизации документации;
- работы с GitHub в рамках инженерного процесса.

Перед нетривиальной реализацией Codex должен получить продуктовый контекст, критерии приёмки и ограничения.

## 3. GitHub

**Статус:** Primary

GitHub является долговременным источником правды для проекта.

Хранить здесь:

- код;
- `AGENTS.md`;
- skills и agents;
- продуктовую документацию;
- решения;
- issues/tasks, если проект использует их;
- PR и review;
- CI-проверки.

Чат не должен быть единственным местом, где существует важное решение.

## 4. Figma

**Статус:** Primary

Главный инструмент для визуального проектирования продукта.

Использовать для:

- UX-flow, если нужна визуальная схема;
- wireframes;
- UI-концептов;
- экранов;
- компонентов;
- вариантов и состояний;
- дизайн-системы;
- интерактивных прототипов;
- visual QA относительно реализации.

Перед переносом дизайна в разработку должны быть понятны не только красивые экраны, но и состояния, responsive-поведение и правила компонентов.

## 5. Cursor

**Статус:** Secondary

Не конкурирует с Codex за одну и ту же ветку одновременно.

Использовать, когда:

- нужен IDE-first workflow;
- удобнее выполнять небольшие локальные изменения прямо рядом с кодом;
- нужен специфический Cursor plugin или MCP;
- задача лучше решается интерактивно внутри редактора.

### Правило

```text
одна ветка/worktree → один пишущий coding-agent в конкретный момент
```

Если работу начинает Cursor после Codex или наоборот, сначала должен быть обновлён `CURRENT_STATE.md` или handoff.

## 6. Product Design

**Статус:** Secondary

Использовать как специализированный дизайн-контур для:

- UX-аудита существующего flow;
- быстрых продуктовых исследований;
- генерации нескольких UI-направлений;
- прототипирования из скриншота;
- клонирования интерфейсной структуры из URL для исследования;
- image-to-code;
- prototype QA.

Это хороший мост между «обсудить в ChatGPT» и «довести в Figma/коде».

## 7. n8n

**Статус:** Project-specific

Использовать, когда автоматизация должна жить как воспроизводимый процесс, а не как длинная цепочка ручных действий.

Подходит для:

- интеграций API;
- webhook-сценариев;
- Telegram/CRM/email automation;
- расписаний;
- AI pipelines;
- обработки входящих данных;
- служебных уведомлений.

Не переносить в n8n простую бизнес-логику только потому, что её можно нарисовать блоками.

## 8. Adobe / Photoshop

**Статус:** Project-specific

Использовать для растровой работы, где генерация изображения уже не заменяет точное редактирование:

- ретушь;
- композитинг;
- подготовка рекламных материалов;
- вырезание и замена элементов;
- унификация серии изображений;
- экспорт производственных ассетов.

## 9. Remotion

**Статус:** Project-specific

Использовать для видео, которое выгоднее описать программно:

- серийные ролики;
- шаблонные анимации;
- data-driven видео;
- автоматическая сборка вариаций;
- интеграция видео-рендера в pipeline.

Для разовой ручной монтажной работы Remotion может оказаться избыточным.

## 10. Browser / Playwright

**Статус:** Primary для web QA

Использовать не только после реализации, но и во время неё.

Проверять:

- критический пользовательский путь;
- responsive;
- формы;
- ошибки;
- навигацию;
- regression scenarios;
- screenshots до/после;
- консоль и network при необходимости.

Скриншот одной страницы не заменяет прохождение интерактивного сценария.

## 11. Yandex Wordstat

**Статус:** Project-specific

Использовать, когда продуктовая гипотеза зависит от поискового спроса:

- оценка частотности;
- сравнение формулировок;
- поиск смежных запросов;
- оценка ниш для контентных и SEO-проектов.

Wordstat показывает поисковое поведение, но сам по себе не доказывает готовность платить или продуктовую ценность.

## 12. Gmail, Google Calendar и Google Contacts

**Статус:** Supporting

Используются как операционный слой вокруг продукта:

- Gmail — коммуникация;
- Calendar — встречи и временные обязательства;
- Contacts — разрешение людей и контактных данных.

Не переносить решения из переписки в продуктовую документацию вручную «когда-нибудь потом»: существенное решение должно попасть в source of truth сразу после принятия.

## Предпочтительные связки

### Новая продуктовая идея

```text
ChatGPT
→ PROJECT_BRIEF
→ Product Design / Figma
→ Codex
→ GitHub
```

### Новая функция

```text
ChatGPT: outcome + requirements
→ Figma/Product Design: flow + states
→ Codex: plan + implementation
→ Browser/Playwright: verification
→ GitHub: PR + history
```

### Исправление UI-багов

```text
Browser/Playwright: reproduce
→ Figma: source of truth, если проблема визуальная
→ Codex: root cause + fix
→ Browser/Playwright: regression check
→ GitHub: review
```

### Автоматизированный сервис

```text
ChatGPT: product flow
→ Codex: core application/API
→ n8n: orchestration/integrations where justified
→ GitHub: source of truth
```

### Генерация серии видео

```text
ChatGPT: сценарий и структура
→ Adobe / image tools: assets
→ Remotion: программная сборка
→ Codex: автоматизация pipeline
```

## Как выбирать новый инструмент

Новый сервис добавляется в основной стек только если он:

1. решает повторяющуюся проблему;
2. заметно лучше текущего инструмента в конкретной роли;
3. не создаёт второй источник правды;
4. имеет понятный экспорт или способ выйти из сервиса;
5. оправдывает стоимость и новый контекст;
6. не создаёт неоправданный риск для данных и секретов.

Перед добавлением спроси:

```text
Что этот инструмент заменяет или улучшает?
```

Если ответ «ничего, просто выглядит интересно», он остаётся Experimental.

## Правило обновления

Если рабочий процесс реально изменился, обнови эту карту. Не добавляй сюда сервис после одного случайного теста. Документ должен отражать фактический рабочий стек, а не коллекцию закладок.
