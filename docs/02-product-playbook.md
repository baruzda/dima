# Продуктовый playbook

> Status: APPROVED  
> Authority: CANONICAL  
> Last reviewed: 2026-08-16

## Формула продукта

```text
Для [пользователь]
в ситуации [контекст]
продукт помогает [желаемый исход]
лучше текущей альтернативы [альтернатива]
за счёт [ключевой механизм].
```

Пока формулу нельзя заполнить без туманных слов, рано выбирать фреймворк и рисовать экраны.

## Четыре типа утверждений

| Тип | Значение | Пример |
|---|---|---|
| Факт | подтверждён наблюдением или данными | 38% пользователей покидают форму на шаге оплаты |
| Гипотеза | проверяемое предположение | сохранение черновика снизит отказы |
| Допущение | временно принятое условие | в MVP работает только один регион |
| Решение | выбранный курс с причиной | используем email вместо телефона из-за стоимости SMS |

Не выдавай допущение за пользовательское исследование. У каждой важной гипотезы должен быть способ проверки.

## JTBD

Формат:

```text
Когда [ситуация],
я хочу [мотивация/действие],
чтобы [ожидаемый прогресс].
```

Хороший JTBD описывает прогресс пользователя, а не кнопку продукта.

## Границы MVP

Разделяй:

- **MVP:** без этого основной сценарий не даёт ценность;
- **Next:** логичное продолжение после доказательства ядра;
- **Not now:** сознательно отложено;
- **Unknown:** требует исследования или решения.

MVP должен содержать один сквозной сценарий и минимальную поддержку его ошибок. Коллекция красивых экранов без завершённого результата не является MVP.

## Метрики

Используй минимум три уровня:

1. **Outcome:** достиг ли пользователь результата.
2. **Behavior:** прошёл ли ключевой сценарий.
3. **Guardrail:** не ухудшили ли скорость, ошибки, жалобы или приватность.

Пример:

```text
Outcome: доля успешно созданных заявок.
Behavior: завершение формы после начала.
Guardrail: ошибки API и обращения в поддержку.
```

## Критерии приёмки

Критерий должен наблюдаться:

```gherkin
Given пользователь находится на форме
When он отправляет валидные данные
Then заявка создаётся один раз
And пользователь видит подтверждение и номер заявки
```

Избегай критериев «удобно», «быстро» и «современно» без измеримого определения.

## Дешёвая проверка гипотезы

Перед разработкой спроси:

- можно ли проверить ценность интервью;
- можно ли показать кликабельный прототип;
- можно ли выполнить услугу вручную;
- можно ли измерить текущий путь;
- можно ли сделать feature flag или ограниченный запуск.

## Выход продуктового этапа

- `PROJECT_BRIEF.md`;
- основной JTBD;
- MVP и `Not now`;
- метрики;
- критерии приёмки;
- риски и открытые вопросы;
- один рекомендуемый вертикальный срез.
