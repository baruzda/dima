# Операционная модель

> Status: APPROVED  
> Authority: CANONICAL  
> Last reviewed: 2026-08-16

## Зачем она нужна

Модель хорошо пишет код, но не угадывает продуктовый контракт, скрытые ограничения и критерии качества. Поэтому любая нетривиальная работа проходит через четыре режима.

| Режим | Результат | Разрешены изменения |
|---|---|---|
| `EXPLORE` | факты, карта системы, вопросы и риски | нет |
| `DECIDE` | выбранный подход и зафиксированные границы | только документы решений |
| `BUILD` | минимальный рабочий срез | да, в согласованном scope |
| `REVIEW` | независимые findings и verdict | нет |

Не смешивай `BUILD` и `REVIEW` в одном проходе. Автор патча склонен подтверждать собственную версию реальности.

## Контракт задачи

Перед реализацией зафиксируй шесть полей:

```markdown
## Outcome
Какой наблюдаемый результат должен получить пользователь или система.

## Context
Почему это нужно и как устроено сейчас.

## Constraints
Стек, сроки, совместимость, дизайн-система, приватность и другие рамки.

## Scope
Что меняем и какие области разрешено затронуть.

## Done
Проверяемые критерии приёмки.

## Authority
Что можно менять самостоятельно, а что требует подтверждения.
```

Фразы «сделай красиво», «улучши UX» и «добавь авторизацию» не являются готовыми задачами. Их сначала нужно разложить на результат и критерии.

## Минимальный вертикальный срез

Предпочитай маленький сквозной результат, который проходит через необходимые слои и доступен для проверки. Например:

```text
пользователь вводит email
→ получает понятную валидацию
→ запрос уходит в API
→ успешный ответ отображается
→ ошибка допускает повтор
→ поведение покрыто тестом
```

Это полезнее, чем пять незавершённых слоёв по горизонтали.

## Границы разрешений

### Можно без отдельного подтверждения

- читать репозиторий и документацию;
- запускать безопасные локальные проверки;
- изменять файлы внутри явно запрошенного scope;
- добавлять тесты для заявленного поведения;
- обновлять связанную документацию.

### Требует отдельного подтверждения

- push, merge, release и deploy;
- удаление данных и необратимые миграции;
- создание платных ресурсов;
- изменение production, DNS, секретов и внешних аккаунтов;
- существенное расширение scope;
- смена архитектуры или публичных контрактов.

## Состояние перед началом

Перед изменениями проверь:

```bash
git status --short
git branch --show-current
git log -5 --oneline
```

Незнакомые незакоммиченные изменения являются стоп-сигналом. Не удаляй, не форматируй и не включай их в свой патч.

## Формат завершения

Каждая завершённая работа заканчивается отчётом:

```markdown
## Сделано
## Изменённые файлы
## Проверено
## Доказательства
## Ограничения и риски
## Следующий рекомендуемый шаг
```
