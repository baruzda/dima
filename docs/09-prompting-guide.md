# Постановка задач Codex и ChatGPT

> Status: APPROVED  
> Authority: CANONICAL  
> Last reviewed: 2026-08-16

## Рабочая формула

Сильная постановка содержит:

```text
Outcome + Context + Constraints + Scope + Done + Evidence + Permissions
```

Не обязательно писать роман. Достаточно убрать опасные пробелы.

## Шаблон реализации

```markdown
Нужно: [наблюдаемый результат].

Контекст:
- [как работает сейчас]
- [связанные документы/макеты/файлы]

Ограничения:
- [стек, дизайн-система, совместимость]
- не расширяй scope;
- не добавляй зависимости без необходимости.

Критерии:
1. [проверяемое поведение]
2. [ошибка/состояние]
3. [responsive/accessibility]
4. [тест или команда]

Сначала изучи фактический путь и составь короткий план.
После реализации запусти проверки, проведи read-only review и обнови документацию.
Не push/merge/deploy без отдельного разрешения.
```

## Шаблон UX

```markdown
Используй навык ux-flow.

Пользователь:
Проблема:
JTBD:
Точка входа:
Ожидаемый результат:
MVP:
Ограничения:

Опиши основной и альтернативные пути, состояния, тексты, ошибки,
сохранение контекста, доступность и UX-критерии.
Не выбирай визуальный стиль до фиксации flow.
```

## Шаблон UI

```markdown
Используй навык ui-spec.

Источник правды:
Платформы:
Существующая дизайн-система:
Контрольные размеры:
Технические ограничения:

Подготовь структуру, компоненты, токены, состояния, responsive-правила,
accessibility и visual acceptance checklist.
Не вводи новый паттерн без обоснования.
```

## Шаблон исправления ошибки

```markdown
Используй навык bug-triage.

Фактически:
Ожидалось:
Шаги:
Среда:
Влияние:

Сначала воспроизведи и докажи первопричину.
После этого сделай минимальный fix, добавь regression test,
проверь соседние сценарии и обнови документы.
Не маскируй проблему отключением проверок.
```

## Шаблон review

```markdown
Проведи read-only quality-review для [diff/ветка/сценарий].

Проверь:
- критерии приёмки;
- продуктовый смысл;
- UX/UI и состояния;
- код и контракты;
- тесты;
- доступность;
- безопасность;
- документацию.

Верни только доказуемые findings с P0-P3,
затем verdict, пройденные проверки и остаточные риски.
Файлы не меняй.
```

## Нежелательные формулировки

| Слабая | Лучше |
|---|---|
| Сделай современно | Соблюди указанную систему, визуальную иерархию и критерии |
| Почини всё | Воспроизведи конкретный дефект и ограничь исправление |
| Сделай приложение | Начни с брифа и одного вертикального сценария |
| Оптимизируй код | Назови метрику, узкое место и способ измерения |
| Сам реши | Перечисли границы автономности и точки подтверждения |

## Диалог с моделью

- проси рекомендованный вариант, а не бесконечный каталог;
- отделяй исследование от реализации;
- давай модели реальные файлы и контекст;
- требуй доказательства и команды проверок;
- фиксируй решения в репозитории;
- начинай следующую сессию с `CURRENT_STATE.md`, а не с пересказа чата.
