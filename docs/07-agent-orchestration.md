# Оркестрация агентов

> Status: APPROVED  
> Authority: CANONICAL  
> Last reviewed: 2026-08-16

## Зачем нужны роли

Роль ограничивает угол обзора. Она полезна, когда конкретная ошибка дороже дополнительного прохода. Не запускай восемь агентов на изменение подписи кнопки.

## Роли комплекта

| Агент | Главный вопрос | Запись |
|---|---|---|
| `product_strategist` | решаем ли нужную проблему | нет |
| `ux_architect` | завершает ли сценарий задачу | нет |
| `ui_reviewer` | реализуема и системна ли визуальная модель | нет |
| `code_mapper` | где реально проходит изменение | нет |
| `implementation_worker` | как сделать утверждённый срез | да |
| `qa_reviewer` | что сломано или не доказано | нет |
| `docs_keeper` | соответствует ли источник правды фактам | да, только docs |
| `security_reviewer` | какие доверительные границы и угрозы затронуты | нет |

## Главный агент

Оркестратор:

1. формулирует задачу;
2. разделяет независимые вопросы;
3. выбирает роли;
4. задаёт каждому ограниченный scope;
5. собирает доказательства;
6. разрешает противоречия;
7. принимает единое решение;
8. отвечает за итоговую проверку.

Субагент не должен менять продуктовый scope самостоятельно.

## Когда полезен параллелизм

Безопасно параллелить:

- продуктовый анализ и карту кода;
- UX-review и security-review;
- независимые исследования разных модулей;
- read-only проверку разных критериев.

Опасно параллелить:

- запись в одни файлы;
- миграцию и реализацию её потребителя без согласованного контракта;
- два рефакторинга одной области;
- документацию до стабилизации решения;
- Codex и другой coding-agent в одной ветке с незакоммиченными изменениями.

## Параллельная реализация

Используй отдельные ветки или worktrees, когда:

- области файлов действительно разделены;
- контракты заранее зафиксированы;
- у каждой ветки есть собственная проверка;
- интеграция запланирована отдельно.

Один worktree и одна ветка должны иметь одного пишущего владельца в конкретный момент.

## Контракт делегирования

```markdown
## Role
## Goal
## Scope
## Inputs
## Constraints
## Do not change
## Expected output
## Evidence required
```

## Контракт возврата

Каждый субагент возвращает:

```markdown
## Conclusion
## Evidence
## Findings by priority
## Risks / unknowns
## Recommended action
```

Фраза «всё выглядит нормально» без перечисления проверенного не является review.
