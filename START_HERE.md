# Начни отсюда

Этот файл для первого запуска. Не пытайся сразу включить все роли и построить идеальную архитектуру. Цель первой недели: научиться давать модели ограниченную задачу, получать проверяемый результат и не терять контекст.

## 1. Подключи комплект к учебному проекту

```bash
git clone https://github.com/baruzda/dima.git
cd dima
bash scripts/bootstrap-project.sh /путь/к/учебному-проекту
```

Открой учебный проект в Codex. Убедись, что видны навыки:

```text
/skills
```

## 2. Не начинай с кода

Вызови:

```text
$project-kickoff
```

И добавь:

```text
Изучи проект и заполни продуктовую основу.
Не реализуй код.
Зафиксируй пользователя, проблему, основной сценарий,
границы MVP, критерии готовности и первый вертикальный срез.
Неизвестное пометь как допущение.
```

Проверь созданные документы в `docs/project/`. Они должны быть понятны без старого чата.

## 3. Спроектируй один сценарий

```text
$ux-flow

Возьми основной сценарий из PROJECT_BRIEF.md.
Опиши путь, состояния, ошибки, тексты, возвраты,
доступность и UX-критерии.
Не переходи к визуальному стилю.
```

## 4. Получи план по реальному коду

```text
$implementation-plan

Изучи фактический код и подготовь минимальный план
первого вертикального среза.
Для каждого шага укажи файлы, риски и проверку.
Файлы не меняй.
```

План должен ссылаться на реальные файлы и команды. Общие слова без карты кода отправляй на доработку.

## 5. Реализуй маленький срез

```text
$build-feature

Реализуй утверждённый первый срез.
Не расширяй scope и не добавляй зависимости без необходимости.
Запусти релевантные проверки, затем обнови CURRENT_STATE.md.
Не push, merge или deploy.
```

## 6. Отдели проверку от автора

```text
$quality-review

Проведи независимый read-only review текущего diff.
Проверь критерии, UX-состояния, код, тесты,
доступность, безопасность и документацию.
Верни доказуемые findings P0-P3 и verdict.
```

Сначала исправляй `P0` и `P1`. Не трать вечер на декоративный `P3`, пока основной путь хромает.

## Три главных правила

1. **Дай источник правды.** Файл и код лучше пересказа.
2. **Ограничь область.** Одна задача, один наблюдаемый исход.
3. **Потребуй доказательство.** Команды, тесты, сценарий или скриншот.

## Когда остановиться

Останови реализацию, если:

- есть незнакомые незакоммиченные изменения;
- требования конфликтуют;
- нужен необратимый шаг;
- меняется production или внешний сервис;
- модель предлагает широкий рефакторинг без необходимости;
- результат невозможно проверить.

## Нормальный ритм

```text
бриф → flow → план → маленький патч → проверки → review → docs
```

Не нужно вызывать все навыки для каждой запятой. Используй процесс пропорционально риску.
